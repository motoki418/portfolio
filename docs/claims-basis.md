# 公開数値の換算基準（正本）

katachi-ai.com で公開する実績・効果の数値は、**すべてこのファイルの基準で導出する**。
ページごとに違う係数で換算すると、同じ事例から違う数字が出て（実際に発生した＝bd `katachi-fkc`）、
読者にも AI 検索エンジンにも「どちらかが誤り」と判定される。

## 1. 換算係数（2026-07-26 決定・オーナー承認済み）

| 単位 | 係数 | 根拠 |
| --- | --- | --- |
| 1ヶ月 | 4 稼働週 | 祝日・年末年始・夏季休暇等を控除した実稼働ベース |
| 1年 | 48 稼働週 ＝ 12ヶ月 | 暦の52週から休暇・繁閑を控除。控えめ側に倒す |

- 週 → 月：**×4**
- 週 → 年：**×48**
- 月 → 年：**×12**

暦どおりの52週（月19.5時間相当）は採らない。上限値での見せ方になり、景品表示法上の
優良誤認リスクと、顧客が実感する値との乖離が大きくなるため。

## 2. 現在公開している事例の導出値

元数値（`index.html` の `case-metric` / `hero-stat-value`）は支援の実測値。
年・月換算は**この係数で導いた試算**であり、実測値ではない。

| 事例 | 元数値（実測） | 増える時間／週 | ／月 | ／年 |
| --- | --- | --- | --- | --- |
| 製造業・見積書の作成 | 週5時間 → 30分 | 4.5時間 | 18時間 | 216時間 |
| 士業・顧客への定型連絡 | 月30時間を削減 | 7.5時間 | 30時間 | 360時間 |
| 美容室・予約確認の電話 | 週8時間 → 30分 | 7.5時間 | 30時間 | 360時間 |

## 3. 表記ルール

1. **新規・改訂するコピーは獲得フレームで書く**。「工数を削減」ではなく「◯◯に回せる時間が増える」。
   （2026-07-23 高木MTG の方針。LP・提案・商談すべてに適用）
   既存コピーの一括変換はこのルールの対象外＝下記4を参照。公開中の主張を書き換えるのは
   営業判断であり、表記ルールの適用として黙って行わない。
2. **派生値を「実測値」と呼ばない**。年換算・月換算を載せる箇所では
   「年48稼働週で換算」のように基準を併記するか、試算である旨がわかる書き方にする。
3. **切り上げない**。216時間を「約220時間」と丸めない（上振れ方向の丸めは優良誤認側に効く）。
   丸めるなら「200時間超」のように下振れ側にする。
4. 元数値そのもの（週5時間 → 30分 等）を変えるときは、この表と `index.html` の
   `hero-stat-value` / `case-metric`、および `tests/e2e.spec.ts` のガードを同時に更新する。

## 4. 未適用の箇所

- **削減フレームで残っているコピー**（ルール1の未適用分）:
  `index.html` の `hero-stat-value` / `case-metric` にある士業事例「月30時間を削減」。
  上表にもそのまま載せてある。獲得フレームへの言い換えは公開中の主張の変更に当たるため、
  オーナー判断を経てから行う（bd `katachi-aq6`）。

- **かんたん診断セクション**（bd `katachi-7oj`、`mock-first/diagnosis-section/` で作成中）:
  `matrix.json` の `gainLines` が「1年で約220時間」となっており、上記ルール3に反する。
  本番公開時に「年間216時間」へ揃えること。あわせて「※数字は実際の支援事例の実測値です」
  という注記は、年換算が試算である以上そのままでは使えない。

## 5. 検査

`tests/e2e.spec.ts` の「公開数値の一貫性ガード」が、`index.html` の
`pricing-roi` に載る換算値がこの表と一致することを検査する。
基準を変えるときは、この文書 → ガード → 各ページの順で更新する。

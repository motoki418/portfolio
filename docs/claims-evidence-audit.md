# 公開している主張の証拠棚卸し（bd katachi-88t.3 の着手前監査）

## 0. この文書の目的と、次に誰が何をするか

katachi-ai.com が現在公開している「実績・効果・経歴・制度」に関する主張を全数洗い出し、
**それぞれを検証可能にするために誰が何を確認すればよいか**を1枚にまとめたもの。
bd `katachi-88t.3`（実績を検証可能な事例ページへ変換する）の受け入れ条件は
「各事例の内部証拠台帳と公開許諾があり、少なくとも3件が独立URLで公開され、数値の計算方法・
期間・更新日が明記」だが、**2026-07-27 時点で、効果計測の証拠台帳も公開許諾の記録も見当たらない**
（`~/work/clients/` に議事録・ヒアリング記録という素材はあるが台帳形式ではなく、公開3事例との
対応も未確認＝§1 危2）。台帳を作るための一次情報（計測期間・対象件数・計測方法）と公開許諾は、
顧客に確認しない限り手に入らず、これはオーナー本人にしかできない。
したがって事例ページの執筆は着手できない。

**次にやること（順序）**: ①§1 の危1 をオーナーが自分の記憶だけで即答する（顧客への連絡不要・
今日中に白黒つく） → ②§4 のテンプレートで顧客3件に連絡し許諾と一次情報を取る →
③§5 の台帳を `~/work/clients/` 配下に作る → ④台帳が揃った事例だけを独立URLのページにする。
①で「事例の一部が実支援ではない／完了していない」と判明した場合は、②より先に
公開中の表記を直すのが先決になる（§1 危1 の是正案を参照）。

- 基準: コミット `3dce17f`（2026-07-27）＋同日の作業ツリー実測。以下の行番号はこの時点のもの。
  ただし `downloads/ai-readiness-checklist.html` と `tests/e2e.spec.ts` は
  同日に別作業（PDF ドリフトガード）で編集中のため、この2ファイルの行番号は変動しうる。
  引用文字列で再検索すること。
- この文書は公開リポジトリに置くため、**顧客名・担当者名・特定可能な情報は一切書かない**。
  それらは §5 の非公開台帳側にだけ書く。

## 1. 危険度順の指摘

### 危1（最優先）事例の「試作1ヶ月＋定着2ヶ月」が、独立時期と時系列で噛み合わない

リポジトリ内の事実だけで矛盾が出る。顧客に聞くまでもなく、オーナーが即答できるはず。

| 確認できる事実 | 出典 |
| --- | --- |
| 独立は 2026年5月 | `about/index.html:660`（career-period「2026年5月〜現在」）、`index.html:2280` |
| 3事例はいずれも「試作1ヶ月 ＋ 定着2ヶ月」＝1件あたり3ヶ月 | `index.html:1701,1705,1709,1798,1806,1814` |
| 3事例の数値がLPに初掲載されたのは 2026-06-11 | `git log -S'case-metric' -- index.html` → `6e7c4e7`（導入事例セクション追加, #12）、`0b1b5b4`（hero 実績数値カード, #13）いずれも 2026-06-11 |
| **完了形の断定**「1ヶ月の試作と2ヶ月の定着支援で成果につながった事例です」の初出も 2026-06-11 | `git log -S'1ヶ月の試作と2ヶ月の定着' -- index.html` → `6e7c4e7`（2026-06-11）。掲載箇所は `index.html:1820` |
| 各事例への期間ラベル「試作1ヶ月 ＋ 定着2ヶ月」が付いたのは 2026-06-28 | `git log -S'試作1ヶ月' -- index.html` / `-S'case-period'` → `cb021b0`（LPのCV改善, #33） |

独立（2026年5月）に開始した3ヶ月工程は、最速でも 2026年8月 にしか完了しない。
ところが完了形の断定は **2026-06-11**（独立から約1.4ヶ月）に、期間ラベルは **2026-06-28**
（同 約2ヶ月）に公開されている。**本監査時点（2026-07-27）ですら、独立直後に始めた3ヶ月工程は
まだ完了していない計算**になる。したがって3件とも独立後に完了したという読み方は成立しない。
ありうる実態は次のいずれかで、どれであっても現在の表記は修正か注記が要る。

1. 独立前（副業・前職期間中）の支援である → 「実際の支援で出た成果」は維持できるが、
   実施時期を明示しないと読者は独立後の実績と誤読する。
2. 支援は継続中で「定着2ヶ月」がまだ完了していない → 完了形の `cases-note`（`index.html:1820`）と
   `case-period` が事実と違う。「試作1ヶ月＋定着2ヶ月で進行中」等へ要修正。
3. 期間は実績ではなく標準工程（＝これから提供する予定の進め方）を事例欄に書いた
   → 事例の属性として書いてはいけない。標準工程は `#process` 側に書く情報。
4. 事例が実支援ではなく想定・複合である → 「実際の支援で出た成果」（`index.html:1699`,
   `services/ai-workflow-automation/index.html:874`）は取り下げが必要。

景品表示法の優良誤認（合理的根拠の提出を求められる対象）に最も近いのがこの項目。
`services/` 側の FAQ が「目安は試作1ヶ月＋定着2ヶ月」（`:1128`, JSON-LD `:77`）と
**同じ数字を"目安"として再利用している**ため、実績なのか標準工程なのかが読者から区別できない
状態になっている点も、この曖昧さを増幅している。

**是正の方向（オーナー判断）**: 実施時期（年月）を `case-period` に併記するのが最小の修正。
「2026年◯月〜◯月に実施」と書けば、期間が実績か工程かの曖昧さも同時に消える。

### 危2 3事例の元数値が「実測値」と正本に断定されているが、実測の証拠が1つも存在しない

`docs/claims-basis.md:23` は「元数値（`index.html` の `case-metric` / `hero-stat-value`）は
支援の実測値」と断定している。しかし、その実測を裏付ける計測期間・対象件数・計測方法・計測者の
記録は見当たらない。

`~/work/clients/` の状況（2026-07-27 実測。**ファイル名の一覧のみ確認。中身は顧客データ最小化の
ため精査していない**）:

- 7案件分のフォルダに計46ファイル。内訳は README・議事録・ヒアリングメモ／台本／議事録評価・
  提案書・見積書・業務委託契約書ドラフト・商談の文字起こし・LINE履歴・営業デモ台帳。
- **Before/After の効果計測を記録したファイルは、ファイル名の水準では1つも無い**
  （「計測」「効果」「実績」を含むファイル名がゼロ）。
- 公開3事例（製造業＝見積書の作成／士業＝顧客への定型連絡／美容室＝予約確認の電話）に
  対応するフォルダは、**名称からは特定できない**。フォルダ名が示す案件はサイト制作・
  セミナー・勉強会・ニュースレター等で、公開事例の業務内容と一致しない。

つまり「台帳がゼロ」ではなく「**議事録・ヒアリング記録という素材はあるが、効果計測の台帳形式には
なっておらず、公開3事例との対応も未確認**」が正確な現在地。素材の中に §5 の台帳項目を部分的に
埋められる記述があるかは、オーナー本人が中身を確認する必要がある（顧客データを監査目的で
横断精読するのは避けた）。いずれにせよ、現時点で「実測値」と断定できる根拠は提示されていない。

- 公開側は `hero-stats-label`「実際の支援で出た成果」（`index.html:1699` /
  `services/…:874`）、`aria-label="支援実績"`（`index.html:1698` / `services/…:873`）、
  「実際の支援事例です」（`index.html:1793`）と、実測であることを3通りの言い方で断定している。
- `tests/e2e.spec.ts:256-269` の一貫性ガードは**換算の整合しか見ていない**（216時間になっているか）。
  元数値が実測かどうかは決定論テストで検査できない。**ガードが緑でも元数値の真偽は担保されない**。
  緑を「検証済み」と読まないこと。
- 2026-07-26 の別レビュー（`mock-first/diagnosis-section/REVIEW-2026-07-26.html`）も
  「実在する支援事例は3件だけです」と書いているが、その根拠は `index.html:1701-1710` と
  `1797-1816` の読み取り＝**主張そのものを主張の根拠にしている循環**であり、一次証拠の照合ではない。

Before/After を後から再構成できるかがカギ。`§4-2` の質問で「Before をどう測ったか」を
顧客から取れなければ、その数値は「実測値」表記をやめて試算・目安に落とす必要がある。

### 危3 士業事例だけ Before が無く、単位も他2件と異なる

| 事例 | 公開表記 | 形式 | 出典 |
| --- | --- | --- | --- |
| 製造業 | 週5時間 → 30分 | Before/After 両方あり（週） | `index.html:1702,1799` |
| 士業 | 月30時間を削減 | **差分のみ・Before 不明**（月） | `index.html:1706,1807` |
| 美容室 | 週8時間 → 30分 | Before/After 両方あり（週） | `index.html:1710,1815` |

- Before が無いため削減率が計算できず、「月30時間」が全体の何割なのか読者にも検証できない。
  30時間が対象業務の全量なのか一部なのかで、主張の重みは全く変わる。
- 単位が月のため、`docs/claims-basis.md:29` では週へ割り戻して「7.5時間/週」としている。
  これは他2件（週の元数値から月・年へ積み上げ）と**逆方向の加工**で、同じ表に並んでいながら
  導出の性質が違う。しかも割り戻し結果 7.5時間/週 が美容室事例の 7.5時間/週 と偶然一致しており、
  台帳を見ない読み手には区別がつかない。
- 削減フレームのまま残っている点は bd `katachi-aq6` で既知（獲得フレームへの言い換えは営業判断）。
  ただし**言い換えの前に Before を確定させないと、獲得フレームでも同じ検証不能さが残る**。

### 危4 顧客の声3件が、原文・要約・脚色のどれか判別できず、掲載許諾の記録も無い

`index.html:1801`（製造業）/ `:1809`（士業）/ `:1817`（美容室）。
3件とも一文・同じリズム・同じ結び（「〜になりました」「〜ようになりました」）で揃っており、
そのまま読むと**同一人物が書いた要約**に見える。実際に顧客が発した言葉なのか、
オーナーが会話から要約したのかが文面から判別できない。

`index.html:1820` は「守秘義務のため社名・担当者名は非公開」と書いているが、これは
**非公開にしている説明であって、掲載許諾を得た証拠ではない**。匿名でも、顧客が
「自社のことだ」と特定できる粒度（業種＋業務＋数値＋時期）で公開している以上、許諾は要る。

### 危5 「構造は業種を問わず再現できます」は、3件からの一般化で反証も検証もできない

`index.html:1820`。母数3件（各業種1件）で「業種を問わず再現できる」と言い切っている。
成功率・不成功事例の開示が無いため、読者が検証する手段が無い。
なお `services/ai-workflow-automation/index.html:899-919` には「向かない業務」を明示した節があり、
こちらは適用範囲を限定する良い記述。**同じサイト内で、限定する記述と無限定に一般化する記述が
併存している**のが問題で、`index.html:1820` を services 側の水準（条件付き）に合わせるのが自然。

### 危6 研修の補助金試算だけ補助率が本文に無く、読者が検算できない

`training/index.html:1126`：「10名（研修費 総額60万円）が補助対象となった場合、補助額45万円・
実質負担15万円（1人あたり実質1.5万円）」。45/60 は補助率 **3/4**。

- `index.html:2054` のトップページ側の試算は「補助率1/2以内（賃上げ要件を満たすと2/3以内）」と
  **率を明記**しており、読者が自分で検算できる。training 側だけ率が無く金額だけ。
- 制度が別（training は北海道「賃上げ環境整備補助金2026」を挙げている＝`training/index.html:1127`）
  なので率が違うこと自体は矛盾ではない。問題は**根拠となる率と上限が本文に無いこと**。
- 是正は「補助率3/4・上限◯◯万円（北海道 賃上げ環境整備補助金2026・2026年度公募要領）」の形で
  率と出典年度を併記すること。公募要領の実物突き合わせが必要（顧客確認は不要・オーナー単独で可能）。

### 危7 前職の内部指標「スプリントゴール達成率100%に貢献」は第三者検証が不可能

`index.html:2296` / `about/index.html:676`。前職チームの内部指標であり、外部から確認する手段が無い。
加えて前職の非公開情報に触れる可能性がある。数値を落として「スクラム改善（レトロスペクティブ導入・
デイリー再設計）を担当」の事実記述に留めるのが安全側。
なお「スクラムマスター資格（RSM / PSM I）」（`index.html:2274` ほか）は**発行元で照会可能な
検証可能な主張**で、これは維持してよい（むしろ証明書URLを添えると強くなる）。

### 危8 問い合わせフォームの返信約束に営業日の限定が無い

- `index.html:1880`（契約者向けチャット相談）: 「**営業日**24時間以内に返信」
- `index.html:2377`（問い合わせフォーム送信完了画面）: 「24時間以内に初回のご返信をいたします」

後者に営業日の限定が無く、土日祝に送信された問い合わせで無条件に破綻する約束になっている。
実績数値ほどの重さは無いが、**自分で守れる条件に揃える**のが筋（前者に合わせて「営業日」を足す）。
